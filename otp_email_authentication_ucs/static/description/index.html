Two-Factor Authentication (2FA)

Adds a mandatory, secure Email OTP verification step after standard username and password validation.

Cryptographic Salt Hashing

Plaintext OTPs are never stored in the database or logged; only SHA-256 hashes generated with random salts are stored.

Session Isolation & MFA Hooks

Flexible Expiration & Cooldown

Brute-Force Rate Limiting

Prevents unauthorized access by capping maximum invalid attempt retries and maximum resend requests per challenge.

Audit Log Trail & Security Logs

See It In Action

1. Email OTP Administration & Master Data

Access central administration menus under Settings → Email OTP Security. Easily monitor live master data including OTP Requests (challenge tokens, status, expiration) and complete OTP Audit Logs.

2. User Security Tab & OTP Enforcement

Open any user profile in Settings → Users or user preferences. Under the new Email OTP Security tab, enable the Require OTP & Email Authentication checkbox to enforce OTP security for that user.

3. General Settings OTP Configurations

Under General Settings → OTP & Email Authentication, customize all global security parameters: enable OTP authentication, set OTP code length (4, 6, or 8 digits), expiration timing (minutes), resend cooldown (seconds), maximum retry attempts, and max resend limits.

4. Standard Login Page Authentication

Users log in using their primary credentials (Email & Password) on the standard Odoo web login page. Once primary authentication succeeds, the system automatically triggers the secondary verification flow.

5. Identity Verification & OTP Entry Screen

After clicking Log in, a new Verify Your Identity screen opens. Enter the OTP code delivered to your registered email address, featuring auto-focus input, visual resend timer, and instant login confirmation.

Frequently Asked Questions

Find answers to common questions about the OTP & Email Authentication module.

1. How are OTP verification codes secured in the Odoo database?

OTP codes are never stored as plaintext in the database. When an OTP is generated, the system creates a 16-byte cryptographically secure random salt and computes a SHA-256 hash. During verification, the candidate token is hashed with the stored salt and securely verified to protect against timing attacks and data exposure.

2. Can administrators enforce OTP authentication globally or per user?

Yes. The module supports flexible dual-level enforcement. System administrators can enable OTP authentication globally via General Settings → Enable OTP & Email Authentication, or selectively enable/disable the Require OTP & Email Authentication toggle on individual user profiles.

3. What happens if a user enters an incorrect OTP code multiple times?

The system features built-in brute-force protection. Administrators set a Maximum Verification Attempts threshold (default 5). Each invalid attempt increments the attempt counter and logs an audit record. Once the maximum threshold is reached, the challenge state automatically transitions to failed and invalidates further entries for that token.

4. How does the OTP resend cooldown timer operate on the login screen?

To prevent mail server spamming and automated abuse, a client-side and server-side resend cooldown timer is enforced (configurable in seconds, default 60s). The Resend OTP button displays an interactive countdown timer and remains disabled until the cooldown expires. Additionally, a Maximum Resend Attempts limit (default 3 per session) restricts total re-issuance per login session.

5. Where and how long are security audit logs stored?

All OTP events (generation, email dispatch, resend, verification success, failed attempts, and timeouts) are logged in the dedicated Audit Logs table along with timestamps, user IDs, client IP addresses, and User Agent strings. An automated scheduled action automatically purges old logs beyond the configured retention period (default 90 days).

6. How does the system handle expired OTP codes?

Each OTP challenge is assigned a strict lifespan (configurable in minutes, default 1 minute). If a user attempts to verify an expired token, the backend evaluation automatically updates the challenge state to expired, rejects authentication with an explicit notification, and logs an audit event.

7. Is OTP authentication required for API requests or XML-RPC/JSON-RPC integrations?

External API integrations, scripts, and mobile connectors must use secure Odoo API Keys rather than standard user passwords, safeguarding web login channels without breaking automated background integrations.

8. Can the OTP email template be customized with custom branding and logos?

Yes. The OTP email notification relies on standard Odoo email template definitions. System administrators can easily customize the email layout, headers, messaging text, colors, and logo from Settings → Technical → Email Templates.

9. What happens if a user attempts to log in without a registered email address?

Before issuing an OTP challenge, the system verifies that the target user has a valid email address configured. If no valid email address is found, challenge generation is blocked, an error is raised, and the user is instructed to contact an administrator to update their profile email.

10. How are concurrent or previous pending OTP requests managed when requesting a new code?

To prevent race conditions and token replay attacks, requesting a new OTP code automatically identifies all existing pending challenges for that user session and immediately cancels them. Only the latest active challenge token can be verified.

11. Does the module clean up old OTP challenge records from the database?

Yes. An automated background process runs regularly to delete historical challenge records older than 7 days, maintaining clean database hygiene.

12. What technical mechanism handles the OTP prompt on the web login page?

The module integrates directly into Odoo's native Multi-Factor Authentication pipeline. Upon primary password validation, Odoo redirects the session to a secure verification page, rendering an interactive verification interface with auto-focus inputs, visual resend timer, and instant validation response.

13. What client-side IP and Browser data is captured in security audit logs?

During OTP generation, resend, and verification, the module captures the client request details such as IP address and browser type. This information is stored alongside the audit log entry, enabling security teams to inspect suspicious login attempts from unexpected IP addresses or browsers.
